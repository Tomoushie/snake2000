====================================================================

Règles et Conditions (Version AAA, adaptée à Snake2000)

====================================================================

Sommaire : 

Le moteur Snake2000 est modulaire : chaque fonctionnalité doit être isolée dans un module dédié.
Aucun fichier ne doit contenir plusieurs responsabilités.
Les systèmes doivent être faiblement couplés et fortement cohérents.
Les composants ECS doivent rester purs (données uniquement).
Les outils (profilers, debug, visualisation) doivent être séparés des systèmes de gameplay.
/Engine ne doit contenir aucune logique spécifique au jeu Snake2000.
/Game ne doit contenir aucun système générique du moteur.

Les modules doivent être organisés en :

Components/
System/
Tools/
(optionnel) Data/

Les interactions doivent passer par :

EventBus
Services
Messages
Interfaces

==========================

Contraintes de structure des dossiers:

✔ /Engine
Contient uniquement :

moteurs (Rendering, Audio, Physics, Animation, AI),

systèmes génériques (JobSystem, Profiler, ResourceManager),

pipelines (Rendering, Networking),

outils (Editor, DebugOverlay).

Aucun fichier Snake2000 ne doit apparaître ici.

✔ /Engine/Gameplay
Contient les systèmes AAA génériques :

Buffs
Quests
Dialogue
Cutscenes
Weather
Biomes
Seasons
Stats
Talents
Inventory
Progression

Ces systèmes doivent être indépendants du jeu Snake2000.

✔ /Game
Contient :

la logique du jeu Snake2000,
les modes,
les entités,
les boss,
les systèmes Snake spécifiques,
les modules Snake spécifiques (Movement, Chaos, Fusion, etc.).

✔ /Game/Gameplay/Movement
C’est un module complet.
Il doit contenir :

Components/
System/
Tools/

Aucun autre dossier ne doit contenir du code de locomotion.

1. Principes fondamentaux de l’architecture :

Le moteur Snake2000 est modulaire, chaque module doit être isolé dans un dossier dédié.
Aucun fichier ne doit devenir un “god‑file” contenant plusieurs responsabilités.
Les systèmes doivent être faibles en dépendances, forts en cohérence interne.
Les composants ECS doivent rester purs, sans logique métier.
Les outils (profilers, debug, visualisation) doivent être séparés des systèmes de gameplay.
Le dossier /Engine ne doit contenir aucune logique spécifique au jeu Snake2000.
Le dossier /Game ne doit contenir aucun système générique du moteur.

2. Règles de structure des dossiers :
 
/Engine
Contient uniquement :

les systèmes génériques,
les services globaux,
les moteurs (Rendering, Audio, Physics, AI),
les outils (Profiler, JobSystem, ModManager),
les pipelines (Rendering, Networking, Editor).
Aucun fichier de gameplay Snake2000 ne doit apparaître ici.

/Engine/Gameplay
Contient les systèmes génériques AAA (Buffs, Quests, Dialogue, Cutscenes, Weather, Biomes, Seasons, Stats, Talents, Inventory, Progression).
Ces systèmes doivent être indépendants du jeu Snake2000.

/Game
Contient :

la logique du jeu Snake2000,
les modes,
les entités,
les boss,
les systèmes Snake spécifiques,
les modules Snake spécifiques (Movement, Chaos, Fusion, etc.).

/Game/Gameplay/Movement
C’est un module complet.
Il doit contenir :

Components/
System/
Tools/

Aucun autre dossier ne doit contenir du code de locomotion.

3. Règles de modularité
Chaque module doit avoir son propre dossier.

Chaque module doit contenir :

Components/
System/
Tools/ (si nécessaire)

Aucun module ne doit dépendre directement d’un autre module de gameplay.

Les interactions doivent passer par :

EventBus
Messages
Services
Interfaces

4. Règles de mise à jour (GameEngine.Update)
Le pipeline doit rester strictement ordonné, sans mélange de logique.

Pipeline global :
GameEngine.Update();
Renderer.Draw();

Aucun système ne doit modifier cet ordre sans justification technique.

==============================================

Ordre strict dans GameEngine.Update :

WeatherSystem.Update()
TimeWarpSystem.Update()
BossSystem.Update()
MiniBossSystem.Update()
ChaosSystem.Update()
SnakeSystem.Update()
CollisionSystem.Update()
ParticleSystem.Update()
BattleRoyaleSystem.Update()

Ajouts obligatoires pour Movement :

MovementSystem.Update()
MovementImpactSystem.Update()
MovementAnimationBridgeSystem.Update()
MovementProfiler.Update()
SurfaceReactionSystem.Update()
MovementSoundSystem.Update()

5. Règles “NE PAS TOUCHER”
Ces règles sont adaptées à ton moteur modulaire :

❌ Interdictions absolues :
ne pas réécrire les systèmes existants,
ne pas modifier les algorithmes internes,
ne pas changer les interactions entre systèmes,
ne pas toucher aux modes de jeu,
ne pas modifier les boss,
ne pas changer les particules,
ne pas toucher aux collisions,
ne pas modifier les timers,
ne pas changer les variables globales,
ne pas modifier les enums existants,
ne pas changer les constantes globales.

✔ Autorisé :
ajouter des modules,
séparer des systèmes,
refactoriser la structure des dossiers,
déplacer du code dans des fichiers dédiés,
créer des outils de debug,
créer des profilers,
créer des bridges (Animation, Audio, Physics),
créer des systèmes annexes (Movement, Surfaces, Weather, etc.),
corriger les doublons, incohérences, conflits de nommage.

=======================

6. Problèmes potentiels à surveiller:

🔧 Conflits de nommage
deux classes Particle,

deux enums SpecialKind,

deux méthodes StartBattleRoyale.
→ doivent être renommés ou regroupés.

🔧 Variables manquantes
Certains systèmes utilisent des variables non définies dans :

GameState
GameConfig
SnakeEntity
→ vérifier les dépendances croisées.

🔧 Dépendances circulaires
À éviter absolument :

Movement ↔ Physics ↔ AI ↔ Gameplay,
Boss ↔ GameEngine ↔ Rendering.

🔧 Systèmes trop lourds
Si un système dépasse :

1000 lignes

10 responsabilités
→ il doit être éclaté en sous‑systèmes.

🔧 Surcharge du pipeline Update
Ajouter trop de systèmes peut :

augmenter le coût CPU,

créer des micro‑lags.
→ utiliser LOD, JobSystem, Profiler.

7. Conditions de qualité du moteur

Chaque fichier doit avoir une seule responsabilité.
Chaque système doit être testable indépendamment.
Chaque module doit être documenté dans Structure.txt.
Chaque interaction doit passer par EventBus ou Services.
Chaque dossier doit rester cohérent avec son rôle.s
